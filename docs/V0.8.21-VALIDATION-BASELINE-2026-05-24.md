## Empirical proof v0.8.21 will work — already demonstrated on milkyb

The cleanest evidence is the cross-relay self-heal: **syd anchored Drop within ~5 seconds of getting #24, pulling from fra over Hyperswarm — no external publisher involved**. fra had pulled the blocks from Iain's machine earlier (publisher on swarm). When syd came up with the persistent-download-range fix:

1. syd's `_seedAppInner` ran for Drop's entry (reseed from persistent log)
2. `_registerPersistentDownloads(drop, drive)` registered persistent `core.download({start:0, end:-1})` on Drop's blob core
3. swarm.join(discoveryKey) announced syd on Drop's topic
4. DHT discovered fra (already serving) within seconds
5. syd's blob core's `want` immediately matched fra's available blocks
6. Blocks flowed
7. Periodic anchor check confirmed full blob present → set anchored=true

End-to-end timing: ~5 seconds from deploy completion to syd serving Drop.

Iain's machine separately pulled 3,431 blocks from `0 → 3,431 in 80 seconds` after the fra deploy. Pre-fix on the same fra: `0 blocks for 30+ minutes` with publisher online. The ramp curve (211 → 654 → 1,471 → 3,431) shows hyperswarm's per-connection block-request rate working as designed.

## Known limitations + caveats

**`hiverelay_cores_seeded` metric.** PR #24's persistent-download fix bypasses `seeder.seedCore()` and registers directly via `core.download()`. So the metric won't move from 1 (the registry log core) even though every drive is now actively pulling. Operator visibility into per-drive storage usage is a separate v0.8.22 follow-up (unifying seeder accounting with appRegistry-managed drives).

**iad self-heal lag.** One of the 3 milkyb relays (iad, IAD region) hasn't yet pulled Drop's blocks despite 15h uptime with the fix. fra (EU) and syd (OC) pulled within seconds. Most likely DHT discovery edge case in IAD region (smaller hyperswarm peer set). Not blocking — the mechanism is proven by fra+syd. Worth watching post-v0.8.21 across the foundation fleet's 5 distinct regions to confirm the pattern doesn't repeat for any specific region.

**Per-app cap enforcement.** Persistent download ranges request blocks indefinitely. Initial cap was already enforced once in `_eagerReplicate`'s `getDriveSize` + abort-if-too-big. For drives that grow past the cap *after* initial seed, that's a separate (pre-existing) concern not addressed by #24.

## Snapshot commands (for the post-roll re-run)

```bash
DROP=af8fd7b6e1ceffebaba899aae0bf990d7c0671deaaf08f7eade981c93b1657be

for relay in 'utah:144.172.101.215' 'utah-us:144.172.91.26' \
             'singapore-1:104.194.153.179' 'singapore-2:104.194.152.121' \
             'bern:45.59.123.112'; do
  name=$(echo $relay | cut -d: -f1)
  ip=$(echo $relay | cut -d: -f2)
  doc=$(curl -sS -m 10 "http://${ip}:9100/.well-known/hiverelay.json")
  cat=$(curl -sS -m 10 "http://${ip}:9100/catalog.json")
  cat_totals=$(echo "$doc" | jq -r '.catalog | "\(.anchored)/\(.total)"')
  drop=$(echo "$cat" | jq -r --arg k "$DROP" \
    '.apps[]? | select((.appKey // "") | ascii_downcase == $k) | "anchored=\(.anchored) len=\(.anchoredLength)"')
  echo "$name: catalog=$cat_totals  Drop: ${drop:-absent}"
done
```

Repeat at T+0, T+10min, T+30min, T+60min post-v0.8.21 restart. Diff the anchored counts. That's the field validation section bigd asked for.
