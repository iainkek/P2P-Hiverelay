## The story (so cold-Claude can follow it)

1. **Initial symptom** (2026-05-22): Drop drive (`pear://i687xpzb…`, `af8fd7b6…`, 537 MiB) hung silently for end users running `pear run pear://…`. Bigd's `FEEDBACK-PEARBROWSER-PIN-CAP-FAILURE.md` and `b6ad60e1` confirmed it: relays accepting seeds, then partial-pinning silently. Operators had been bouncing relays as a workaround.

2. **Root cause of the lie** (PR #19): the relay's `anchored` flag was being set on `drive.version > 0` (metadata length), not on actual blob completeness. Three call sites (`_eagerReplicate`, `repairUnanchored`, `_runAnchorCheck`) all had the same bug. `runRepairPass` skips anchored entries, so a partial-pin entry got locked out of its own self-heal path. Fix: new `_isDriveFullyReplicated(drive)` helper using `blob.core.has(0, length)`. All three sites now check completeness before setting anchored.

3. **What #19 unmasked** (PR #22): hyperdrive 11.x changed `drive.download()` from returning a tracker-with-`.done()` to returning a Promise. `cancellable-drive-update.js` was still calling `dl.done()` unconditionally. Pre-#19 this was masked because relays falsely marked themselves anchored on metadata anyway. After #19's honest gate, the broken download surfaced. Fix: API-shape detection — works against both old tracker and new Promise.

4. **What #22 still didn't fix** (PR #24): even with both #19 and #22, drives still never actively requested missing blocks between repair-tick windows. `seeder.seedCore()` registers persistent `core.download({start: 0, end: -1})` "wants" for plain hypercores (the registry log core), but the `appRegistry`-managed Hyperdrive cores never got the same treatment. Metric proof: `hiverelay_cores_seeded=1` across an entire 112-app relay. Fix: new `_registerPersistentDownloads(appKey, drive)` helper called from `_seedAppInner`, stores trackers on `entry.downloadRanges`, destroys on `unseedApp`. Bypasses `seeder.seedCore()` so `cores_seeded` metric stays at 1 (separate issue for v0.8.22+).

5. **The followup investigation** (PR #25 / v0.8.22): after #22 + #24 deployed on milkyb, fra and syd self-healed Drop within seconds (cross-relay pull, no external publisher), but **iad stayed `anchored=false` for 15+ hours**. Hours of investigation found the operational root cause: iad's 1GB Fly volume was 100% full, causing silent `writeFile` hangs on `app-registry.json`. The visible symptoms ALL looked like code bugs in the new persistent-download layer. Two defensive timeout fixes shipped to prevent the cascade from masking the operational issue next time:
   - `drive.ready()` wrapped in 8s timeout in `_seedAppInner` (prevents one hung drive from blocking sequential `reseedFromRegistry`)
   - `_isDriveFullyReplicated` wrapped in 3s timeout (prevents one hung drive from blocking the sequential `_runAnchorCheck` for-loop)
   - Operational fix: extended all 3 milkyb volumes 1→5GB

6. **Validation evidence captured** in this repo:
   - `docs/AUTO-HEAL-ROOT-CAUSE-2026-05-22.md` — full root cause writeup for #19
   - `docs/V0.8.21-VALIDATION-BASELINE-2026-05-24.md` — pre-roll snapshot with the "578 unanchored / 24% of fleet" headline number
   - This doc (HANDOVER-2026-05-24.md)

With v0.8.21+v0.8.22's self-heal actually working, the cross-fleet witness pass should fire correctly for blind-temporary drives. The earlier blocker was "publisher behind NAT can't be reached" — but a foundation relay running the custody-e2e-milkyb-full.mjs script from its own SSH would close that loop.
